# Assessment of the supplied external reviews

Assessed on 2026-11-02 against this checkout (HEAD `a6e16a8`, with the frontend redesign in progress). This evaluates the supplied claims; it does not certify funded execution or change the Rust admission model.

## TradingGYM review

The review identifies a real historical candle discrepancy and a restrictive reservation policy. Several proposed fixes or explanations do not follow from the current source.

| Finding | Assessment | Evidence and disposition |
| --- | --- | --- |
| **F1: reservation deadlock** | **Partly correct: batch limitation, not a deadlock.** | A fresh balance with a different available amount is refused while the previous account/asset batch remains. Contrary to the review, releasing A marks it released; it retains A's original anchor and amount until all batch entries release. B can still settle or be locally denied, after which a new batch can start. See [reservation admission and release](../../executor/exec-core/src/orders.rs), [aggregate reconciliation tests](../../executor/exec-core/tests/order_authority_reservations.rs), and [release/restart/release test](../../executor/exec-svc/tests/offline_reservation_replay.rs). Documenting and permanently testing the mixed-settlement boundary is reasonable. Replacing the anchor equality check alone is unsafe: release still reconciles cumulative batch spend against the original anchor. Supporting overlapping anchors requires an explicit reconciliation and durable-replay contract. |
| **F2: 38.91 bps candle divergence** | **Confirmed historical discrepancy; cause not established by the review.** | At `2026-10-31T08:23:00Z`, the [pre-fix artifact](../../data/live/candle-crosscheck-pre-b1.json) records internal close `76757.5`, venue close `76460`, and exactly half the venue volume. Its counts are 25 AGREE, 1 DIVERGENT, 4 NOT_COVERED. The volume ratio supports investigating collapsed prints; it does not prove the close-ordering cause. Current [collection](../src/gym/services/collector.py) preserves identical prints, with a [regression test](../tests/test_market_data.py). The [later probe](../../data/live/candle-crosscheck-postfix-interim.json) reports 11/11 AGREE in a different window. That smaller probe does not retroactively explain or repair the old minute. Preserve the historical artifact and its source limitations. |
| **F3: zero/tiny spread implies crossed or stale quotes** | **Incorrect inference for the cited samples.** | [Spread statistics](../src/gym/services/market_statistics.py) round to four decimal bps and exclude quotes failing [qualification](../src/gym/domain/bars.py). Read-only inspection of the cited report window found no `bid >= ask` among its 1,352 BTCTMN/BTCUSDT rows. BTCTMN's minimum is bid `21030967289`, ask `21030967290`: a positive one-toman spread, approximately `0.0000004755` bps, displayed as `0.0000`. BTCUSDT's minimum is bid `77310.15`, ask `77310.26`, approximately `0.0142284` bps. Existing [book validation](../src/gym/domain/model.py) already flags crossed and exactly zero spreads. These observations still do not prove executable depth, synchronized sides, or realized trading costs. Comparing different pre/post windows cannot isolate a collector-change effect. |
| **F4: remove terminal-before-ACK transition** | **No defect established; retain the valid ordering race.** | [Order transitions](../../executor/exec-core/src/orders.rs) separate lifecycle, economic effect, and settlement. A terminal event does not itself close an order or release a reservation. An uncertain lost-ACK attempt remains economically unverified and refuses settlement until further evidence resolves it; [chaos tests 08/09](../../executor/exec-core/tests/fake_venue_chaos.rs) exercise both resolved zero-fill and unresolved terminal paths. A direct Submitting attempt does not necessarily have `Unverified` effect, as the review assumes. Removing the transition could reject a real terminal notification that arrives before an ACK. Actual adapters must authenticate and reconcile the evidence supplied to these offline model events. |
| **F5: one entry per account** | **Intentional contract.** | The master specification explicitly requires one unresolved entry per account and one unresolved order per instrument (Section 6.3, decision D13). [Slots](../../executor/exec-core/src/orders.rs) implements this; [chaos test 05](../../executor/exec-core/tests/fake_venue_chaos.rs) preserves independent protective exits on another instrument. This serializes unresolved entries, not all trading forever. Relaxation would be a product/money-contract change. |
| **F6: unused other-instrument entry field** | **Intentional non-veto; optional cleanup only.** | [ExitCheck](../../executor/exec-core/src/c_admission.rs) explicitly states that another instrument's entry must not veto an otherwise valid protective exit. The [exit admission test](../../executor/exec-core/tests/c_admission.rs) supplies `true` and reaches `MissingExecutorAuthority`, rather than an entry-related veto. The input is descriptive; it grants no authority. |
| **F7: Status mode comparison is always satisfied** | **Correct observation, not an authorization bug.** | [StopReply::confirms](../../executor/exec-ipc/src/lib.rs) still requires ACK, matching epoch, and matching correlation. Status imposes no minimum restrictive mode; its purpose is to confirm the response identity and expose the reported mode. It cannot arm or authorize money. [Codec tests](../../executor/exec-ipc/tests/codec.rs) reject stale, mismatched, and weaker stop acknowledgments. A response is an observation, not a promise of future service state. |
| **F8: ledger append unavailable for review** | **Review-window gap resolved by current source.** | [Ledger::open and append](../../executor/exec-store/src/lib.rs) establish and verify WAL/FULL sync, start an IMMEDIATE transaction, check the expected head, insert exact event bytes, commit, and only then update in-memory head/sequence and return. [Durable tests](../../executor/exec-store/tests/durable_ledger.rs) cover reopen, writer exclusion, tampering, sequence gaps, rollback, schema, and size bounds. A fixed event-size limit is not itself a defect. These tests do not establish power-loss behavior on the target hardware. |

The F1 scenario was also checked with a temporary Rust assertion program importing the actual `orders.rs`: reserve A=300 and B=400 against 1000/sequence 10; release A against spent=300, available=700/sequence 11; reject C's changed anchor at sequence 12; settle/release B against cumulative spent=700, available=300/sequence 13; admit C against a new 300/sequence 14 snapshot. No repository code was changed by that probe. The remaining B hold also means the reported 700 available is not wholly unreserved admission capacity.

## Corrections to the review's coverage claims

- Rust and Python already share the genesis bytes and fixed expected digest: [Rust hash tests](../../executor/exec-store/tests/hash_chain.rs) and [Python contract tests](../tests/test_executor_ledger_contract.py). A full Rust-written-ledger-to-Python-reader test would be additional coverage, not the first cross-language golden.
- Stored-byte corruption, rollback, sequence gaps, and a second simultaneous `Ledger::open` are already tested. The writer test uses two handles in one process; it is not a separate-process lock test. A dedicated empty-input `verify_chain` assertion and independent-process lock probe remain distinct optional gaps.
- `Ledger::open` requests WAL and verifies the resulting mode. A database initially using DELETE mode is not inherently rejected if SQLite can convert it to WAL; testing rejection of every initially non-WAL file would assert the wrong behavior.
- `cargo test --all-targets` does **not** run ignored tests by default. Running them requires test-runner options such as `-- --ignored` or `-- --include-ignored`. Thus that CI concern is incorrect.
- Source omitted from the supplied review is a limitation of that review, not proof of a defect. This assessment did not repeat Windows SCM, SID/DACL, installer, service-hang, or target-hardware qualification. Action SHA pinning remains a separate hardening proposal.
